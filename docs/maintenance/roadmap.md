# 后续开发规划

**顺序已确定：先适配功能，用现有 UI 验证；再按产品方美术设计开发新用户端；最后分别封装和验收。** 当前 RC11、工程和快捷方式都只有一个 WinUI 入口。下面的项目拆分是实施建议，功能名单、页面设计和对外发布日留待相应阶段确定。

## 一、用当前面板完成适配

沿用现有九个导航入口及独立框选窗、诊断窗、调试面板。从「引擎」看版本和可用能力，从「测试识别」看逐条件匹配及坐标，从「脚本」「运行设置」「区域监控」复现执行和取消，从「历史」「设置」核对终态、数据及恢复。保留现有 AutomationId，测试数据根及专用输入窗口独立于用户现场。

功能适配一项一项接入。先在服务和契约层定义能力，再在当前面板提供最短可验证路径。每项完成时留下可复用的输入样本、预期、异常处理和回归命令，后续用户端直接调用同一能力。优先处理[首版审查](implementation-review.md)中会影响两端的引擎、数据和输入问题。

| 下一项适配需补的内容 | 当前占位 |
|---|---|
| 目标场景与优先级 | 待产品方提供要支持的对象、使用步骤、样例与理想结果。 |
| 兼容范围 | 登记软件/窗口类型、语言、图片或脚本、支持版本及失败时的反馈。 |
| 技术入口 | 实施时填写所属 Provider 或服务、IPC 命令、能力声明、涉及的旧数据与迁移要求。 |
| 面板验证 | 登记验证页面、专用样本、正常/边界/取消/失效用例、观测位置及通过标准。 |
| 退出条件 | 从现有面板走通，再用相同契约从独立调用方复验。确认需求和依赖后纳入任务/测试索引。 |

## 二、为两套界面拆出公共调用层

在首批功能适配稳定后，从现有应用中逐步提取，不要求先重写页面。以下名称用于说明建议的项目职责。

| 建议工程 | 从哪里起步 | 验收方式 |
|---|---|---|
| 共享客户端类库 | 将现有 `Host/`、`Contracts/` 和嵌入的 schema 转为一个工程引用；保留 ABI、会话事件、请求取消及恢复语义。当前契约测试通过源文件链接复用这些类，应一起改为工程引用。 | 原面板和 C# 契约测试分别编译，运行类型、配置、协议、故障套件，通过进程关闭和回调生命周期测试。 |
| 开发维护应用 | 当前 `desktop/ScreenTrigger/` 演进为维护应用，保留真实页面、覆盖层、识别证据、诊断和 UI 自动化入口。留在视图侧的 `WorkspaceCommands` 当前依赖控件、焦点及 ContentDialog，只提取其中两端确实共用的请求行为。 | 用开发数据根跑既有 UI 自动化，从入口核对显示位置、键盘、焦点、停止和退出。 |
| 用户端应用 | 新建单独 WinUI 3 App 与导航，引用共享客户端。共用后端、宿主和协议，通过受控接口取得捕获、运行和恢复功能。框选几何等生产依赖从探针目录迁入共享位置，探针反向引用。 | 以同一数据和样本在两端比较业务结果、错误及取消，与产品方确认的设计逐页对照。 |

提取的第一步可以只迁移一条只读命令，例如「查看已安装模型」。让面板与契约测试跑通同一调用，再迁移写操作、选择窗口与受控输入。现有主窗承担启动、事件订阅、缓存、焦点和关闭，拆分时逐项指定所有者，避免两套界面各自重写一份安全逻辑。[主窗生命周期](../../desktop/ScreenTrigger/MainWindow.xaml.cs) · [契约测试工程](../../desktop/ScreenTrigger.ContractTests/ScreenTrigger.ContractTests.csproj)

## 三、用户端设计占位

| 设计输入 | 何时填写 | 对应交付 |
|---|---|---|
| 美术稿、字体、图标、色彩与资源授权 | 功能清单稳定、产品方交付设计时 | 设计文件版本、资源清单、WinUI 主题与控件映射 |
| 导航层级与主流程 | 原型评审 | 首次使用、建目标、运行、暂停/停止、调试及恢复的页面关系 |
| 运行与异常状态 | 逐页交互评审 | 加载、缺模型、冲突、取消、失焦、异常退出、键盘焦点与缩放示例 |
| 用户可见能力 | 产品方划定各页边界 | 必须保留的用户功能，以及维护端专用的诊断/实验入口清单 |
| 视觉验收 | 设计定稿后 | 页面、状态、设计版本、截图对照、键盘与焦点检查、产品方确认 |

## 四、分开封装

当前打包脚本接受一个发布目录、检查 `ScreenTrigger.exe` 并写入单一清单入口。安装器使用固定产品名、收据和快捷方式。实施分包时改为两个明确的发布配置，按应用身份生成各自的文件清单、可执行入口、安装根、快捷方式、版本收据与哈希；共用同一版本的宿主、引擎、依赖及模型清单。[介质构建脚本](../../tools/packaging/build_offline.py) · [安装器](../../tools/packaging/Install.ps1) · [卸载器](../../tools/packaging/Uninstall.ps1)

- **用户包**只收录用户入口和所需资源，核对文件清单、启动路由和命令暴露面。升级沿用现有用户数据识别和备份流程。
- **维护包**使用单独的应用名、安装与测试数据目录，可携带诊断和测试资源。共用真实宿主与引擎，保持测试结果有代表性。读取现场数据时先用经过核对的副本。
- **并存与回归**覆盖分别安装、升级其一、卸载其一，并核对另一端入口及数据指纹。两程序争用系统级热键或输入时，建议先实现可见的占用提示和单一输入所有者。若未来需要同时主动控制桌面，再单独设计跨进程仲裁并验证停止链路。
- **切换条件**为两端身份独立，用户包中无维护专用页面、工具或测试数据，维护包仍能完成现有功能回归，用户端可通过已确认的使用流程和视觉验收。安装包与测试证据按各自 SHA-256 关联。

功能适配清单、设计输入与是否需要两端同时接管桌面会影响工程量。当前收尾工期只覆盖既有首版缺口，新增适配、用户端开发与双包交付待这些输入确定后另估。
