# 自查、全局检查与异常闭环

本文件是检查流程的唯一来源。执行约定定义模块边界，任务卡定义交付内容，验收与测试定义业务预期；本文件定义何时检查、如何保存证据、何时可通过及如何处理失败。业务实现与验收状态分别读取账本和当前基线审计。

## 编号、权威来源与逐项目录

- TASK-001–TASK-029 是原子任务；A01–A10 只表示任务组；TEST-001–TEST-016 是全局验收组，互不混用。
- U01–U19 是需求，S01–S09 是成功标准，D01–D12 是技术决策，R01–R11 是风险。决策表中的显式 DEC 编号标识六个冻结检查，调整表格排序或问题措辞不会改变编号。
- [任务卡索引](任务拆解.md)及其分册给出前置、设计、编码、测试与完成条款。[验收矩阵](验收与测试.md)给出场景、断言、测量方法。[需求追踪](../product/审查与需求追踪.md)给出需求到组/规格/测试的映射。
- `python tools/run_acceptance.py catalog` 从上述来源生成 `reports/check-catalog.json`，展开全部原子任务的每条设计、产物、步骤、测试与完成要求，同时加入通用自查项；验收组展开场景和断言，并包含矩阵外测量、成功标准、决策及风险检查。每项保留来源、预期、归属和标识。
- 需求映射展开到任务组中的每个原子任务，并合并任务卡明确引用的需求；这是保守的覆盖映射，不表示每个任务单独实现整个需求。规格条款和直接证据分别保留在目录及报告中。
- 修改任务卡或验收条款会改变基线和检查项哈希，旧证据自动失效。目录由来源生成，不手工维护第二套验收答案。

## 两条链路的触发条件

| 事件 | 必须执行 | 判定与后续 |
|---|---|---|
| 开始任务/接手工作 | baseline；读取硬依赖、决策、既有缺陷和证据 | 先识别现状；不把历史口头结论当实际前置 |
| 完成代码、文档或测试改动，准备声明完成/交接 | 文档检查、相关工具测试、任务逐项自查及 task 审计 | 只有证据有效、依赖通过、决定已冻结、无关联未闭环异常才可 VERIFIED |
| 修复异常或重新打开任务 | 原失败用例、受影响回归、task 审计及当前阶段审计 | 复验失败回到 FIXING，不得用重试覆盖第一次失败 |
| 共享契约、依赖锁、模型、数据集、规格变化 | 基线重算；重验全部被判 STALE 的检查 | 默认保守使所有旧源码基线证据失效，不能继续引用旧通过结果 |
| 测试机、外部数据/模型、负责人决定变化，但仓库文件未变 | 在账本添加 invalidations，列出时间、原因、记录人和受影响 check_ids；重新运行相关检查 | 外部变化不能仅靠源码哈希发现，登记是强制步骤；遗漏登记属于报告缺陷 |
| 申请 P0/P1/P2/P3 退出 | 对应累计阶段审计 | 未通过不进入已验收阶段；可继续独立且前置满足的工作 |
| 新发布候选、安装包重建、发布前 | release 审计，绑定实际产物哈希 | 每个全局验收、测量、成功标准和发布签核都对应同一候选包 |

根目录 [AGENTS.md](../../AGENTS.md) 是后续 Agent 的自动读取入口，要求执行这些触发规则；检查器负责拒绝不满足门槛的完成声明。此机制不依赖 Git 或尚不存在的 CI。接入 CI 时复用相同命令及退出码，不另建宽松门槛。

## 单任务自查与状态转换

实施状态由任务负责人登记：NOT_STARTED → IN_PROGRESS → IMPLEMENTED。IMPLEMENTED 仅表示声称产物已准备，不表示验收通过。

验收状态由检查器计算：NOT_RUN（未实施）、PENDING（缺检查证据）、BLOCKED（前置/决定/异常/无效输入阻塞）、VERIFIED（全部强制检查及硬依赖通过）。不允许手工写 VERIFIED。依赖任务失效会递归阻塞下游验收；修复后由下一次审计重新计算，无需删除历史报告。

逐任务必须核对：

1. **任务专属条款**：设计、实际产物、步骤、测试及完成条款逐项核销。产物证据应列具体文件/入口/接口和检查方法，不能只写目录存在。
2. **构建与契约**：按变更运行构建、语法、类型、静态和契约检查；协议/API/字段修改同步权威文档与相关测试。纯设计任务可对 BUILD 记录有理由、有审查的 N/A。
3. **行为分支**：正常、异常、误操作、边界、超时、重试、取消逐项给出适用性、预期、实际及证据。不能通过整项 N/A 绕过分支清单。
4. **真实环境与交互**：涉及输入的任务核验停止、按键释放、越界、失焦；真实 OS 证据不能由 mock 替代。涉及 UI 检查键盘、焦点、错误提示和普通/调试日志。不涉及 UI 的任务仅可对 UI 项登记有审查的 N/A。
5. **影响回归**：列出接口、依赖和下游受影响范围，运行原失败用例及相应回归；既有失败也必须登记，不因“本次未引入”而删除。未影响项说明依据。
6. **交接**：需求/非目标、修改文件、运行命令、退出码、环境、检查结果、未覆盖、风险、问题单、当前基线和是否可解除下游依赖。说明 TEST 组的哪些子场景已验证，不把 TASK 的局部结果填成全组 PASS。

每个 TASK 有独立检查项；全局 TEST 组必须提交自身全部场景和断言证据。阶段检查允许相关模块子场景随任务逐步通过，整组 TEST 的最终通过只在全量验收中计算。

## 证据、状态与命令

工具只使用 Python 3.13 标准库，不依赖业务 OCR/Lua 或第三方测试包；从项目根目录运行。PowerShell 包装入口分别为 `tools/check-docs.ps1` 和 `tools/run-acceptance.ps1`，可用 `-Python` 指定解释器。

```powershell
python tools/check_docs.py --output reports/docs-validation.json
python -m unittest discover -s tools/tests -v
python tools/run_acceptance.py catalog
python tools/run_acceptance.py audit --scope baseline
python tools/run_acceptance.py audit --task TASK-001
python tools/run_acceptance.py audit --scope P0
python tools/run_acceptance.py audit --scope release
```

退出码 0 表示所请求的门槛通过，1 表示检查失败或尚未就绪，2 表示工具或输入错误。baseline 检查文档、目录、账本和证据有效性。业务放行需查看 task、阶段及 release 各自的门槛与原始结果。

自动命令证据：

```powershell
python tools/run_acceptance.py capture --check TASK-001.BUILD --timeout 600 -- python -m py_compile tools/probes/python_ocr_probe.py
```

该命令检查探针语法。正式 OCR 证据另需实际模型、输入、输出和审查。capture 不使用 shell 拼接，记录命令和原始合并日志；超时或命令不可执行自动记 FAIL，必须闭环。测试命令应自行清理其子进程，不能让后台输入进程继续运行。执行期间基线变化也判失败。

退出 0 只产生 BLOCKED 待审查记录及一份草稿。审查者核对实际断言，补齐环境、实际观察、产物/截图/原始数据等证据，将草稿置为 PASS，填写 review 的 by、at（含时区）、decision=ACCEPT、note，再提交。禁止只根据退出码签核。人工检查使用模板：

```powershell
python tools/run_acceptance.py template --check TASK-001.CONTRACT
python tools/run_acceptance.py submit reports/drafts/实际草稿文件.json
```

template 生成 NOT_RUN 草稿，必须补齐实际开始/结束时间、步骤和证据后才可提交。不得修改旧记录来变绿；每次尝试新 run_id，submit 拒绝覆盖已有记录。review 可以由具备相应职责的 Agent 或负责人完成，产品决定/需求变化必须引用真实授权；工具只能校验审查字段，不能替人判断证据内容。

| 字段/位置 | 约束 |
|---|---|
| run_id、check_id、baseline、spec_sha256 | 唯一运行批次、明确检查项、源文件清单哈希和检查定义哈希；不依赖 Git |
| started_at、finished_at、environment | 带时区时间；实际 OS build、硬件、运行时/锁文件、模型和数据集哈希、适用平台/语言矩阵；不适用项说明 |
| command 或 steps、expected、actual | 完整参数及退出码，或人工复现步骤；预期与实际明确对应 |
| evidence | 非空文件引用数组，每项含仓库内 path 和 sha256；原始日志/截图/测量数据及产物清单可复核 |
| artifact | 发布检查需对应账本 release_artifact 的 path/sha256；capture/template 的 --artifact 可自动填写 |
| review | 具名审查者、时间、ACCEPT 决定、核验说明；时间不早于运行结束 |
| reports/raw、reports/evidence | 原始证据与已提交记录永久保留；缺失/篡改会使审计失败 |
| reports/audits/每次运行 | 独立保存 result.json、catalog.json、summary.md；保留基线清单、每项结果、原因、任务/需求映射和缺陷 |
| reports/latest-audit.json | 仅为最新报告指针，不替代历史证据；所有写入不得指向仓库外 |

逐项原始状态只允许 PASS、FAIL、BLOCKED、NOT_RUN、N/A；STALE 由检查器推导。N/A 只允许目录明确指定的 BUILD/UI 项，并要求理由与审查，独立计数，绝不计为 PASS。安全、业务功能和必需验收项不能用 N/A 跳过。

已提交运行若直接引用将要修订的设计文档，可在 `reports/raw/doc-sha256/<原 SHA-256>.md` 保留经旧基线核对的原字节。历史运行中指向现存 `docs/` 设计 Markdown 或本次列明的八份迁址设计稿的证据，可按回执中的原路径和 SHA-256 核对该副本，结果仍为 STALE 并需重验。当前基线、原始运行日志、归档、安装包及账本所引用的用户授权原文一律按原引用核验。

基线默认涵盖文档、工具、源码、配置、测试和锁文件；排除 reports、构建输出、依赖安装目录、缓存、Git 和工作流状态账本。安装包/外部模型及数据以独立哈希和环境记录约束。保守失效可能需要较多复验，但不会把其他版本结果误当当前通过。

追回历史源码时，将原审计的完整 source_files 清单保存在 `reports/raw/history-baselines/<基线>.json`，将精确原字节保存在 `reports/raw/history-source-sha256/<文件 SHA-256>`。检查器重算清单基线，核对原路径在清单和回执中的哈希一致，再核对副本内容。核验成功的旧回执仍须在当前基线复验。原始运行证据、范围授权、账本、归档和发布包继续按原路径验真。

2026-11-26 用户授权将缺少 19 个源码版本的 43 份历史回执登记作废。账本的范围决定绑定授权原文和逐份清单的哈希。审计保留原回执字节，逐项报告 VOID、缺件与尚待复验的检查。原用例的新 PASS 必须列出对应的 `retested_original_runs`，且该用例及关联回归均须在授权后以当前基线和同一候选包通过。原 FAIL、运行日志、未列入清单的缺件继续按原规则处理。

## 异常闭环与重新打开

本地文件 `docs/agent/check-state.json` 是唯一工作流账本。每个任务有实施状态和负责人；issues 保存问题；invalidations 保存外部变化；scope_changes 保存真实范围决定。运行结果永不手填到此账本。

公开源码可独立运行文档检查、生成检查目录和执行工具回归。实际验收需在授权工作区使用原账本、范围授权原文及 `reports/` 中的证据。仅检出公开源码时，审计会因缺少本地账本返回退出码 2。

异常状态：OPEN → FIXING → READY_FOR_RETEST → CLOSED。严重级别为 critical、major、minor；所有关联必需检查的未关闭异常均阻塞其任务及下游。critical（停止/越界/数据损坏等）立即停止受影响交接；其他项同样不能带失败通过门槛。负责人填写到期时间，逾期向阶段负责人升级，并记录新处置，不以延长日期关闭问题。

问题必须包含：id、check_ids、task_ids、owner、severity、expected、actual、reproduction、created_at、due_at、status、failed_run_ids、regression_checks。首次失败立即登记；环境故障使用 BLOCKED 并登记恢复动作；间歇失败保留所有尝试和定位依据，不以一次成功掩盖。

关闭时增加 fix（description/by/at）、retest_run_ids、closed_by、closed_at。检查器要求原失败检查与全部 regression_checks 都有修复时间之后、当前基线下的 PASS，并核对时间、原始证据和当前结果。没有有效复验的 CLOSED 被判 INVALID 并继续阻塞。FAIL 历史未挂到有效问题单时自动列为 UNTRIAGED；后续 PASS 不会消除该阻塞。

修复后重新检查原用例→受影响回归→任务→当前阶段。全局发现问题时指定责任任务，受影响下游由依赖图阻塞；必要时追加 invalidations。再次失败将问题重开，新的失败 run_id 加入 failed_run_ids。已有安装包发生变化必须重建并更新哈希，重跑对应全量验收。

## 主检查汇总与发布决定

baseline 检查文档/引用/锚点/JSON/归档哈希、目录、账本与证据合法性；阶段模式检查累计任务及适用决策/风险；P3 和 release 再检查全部 TEST 场景/断言、测量方法、S 标准、决策/风险退出与产品签核。

报告分别展示实施状态、验收状态、逐项 PASS/FAIL/BLOCKED/NOT_RUN/N/A/STALE 数量、已验证任务数/范围内任务数、需求覆盖、问题及证据。不以代码文件数量、任务自报数、文档通过数计算产品完成率。证据不足就是未验证，不按未知算通过。

首次生成候选包后，账本 release_artifact 填真实路径和 SHA-256；全部全局证据引用它。发布负责人检查完整报告，产品负责人对用户体验、模型覆盖、建议默认值及最终范围留下 RELEASE.REVIEW 证据。没有包、没有验证、不匹配当前包都不能发布。

范围调整须先取得真实产品授权，scope_changes 记录 id、reason、approved_by、approved_at、version、expires_at、confirmation（证据路径/哈希）、affected_checks；同步规格、任务卡和检查定义，重建基线并重验。记录不会自动豁免检查，也不会将删除/延期项算 PASS。停止后无新增输入、越界不派发等安全不变量不允许豁免。
