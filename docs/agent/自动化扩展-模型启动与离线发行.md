## 标准完全便携发行包

1. 发布者在构建时选择清单中的识别模型 ID。打包器经 `engines` 找到每个 ID 所需的检测与识别模型，共用文件去重。拒绝未知 ID、缺文件和哈希不符。
2. 以本次选中的管线生成该介质自己的目录、模型卡、许可及逐文件清单。识别模型、适用语言和模型元数据都由同一选择派生。公开模型 ID 保持稳定，已有 OCR 条件依此找到原模型。
3. 默认发行包包含两套 OCR 管线，覆盖中、英、日、韩，并包含 OpenCV ORB 特征点匹配。ORB 使用算法和描述子，不增加神经网络权重。YOLO 仅预留识别接口，本版包体与性能验收不计 YOLO 权重、推理引擎或检测效果。
4. 本版交付一个标准完整便携包。使用包内解释器验包。报告 ZIP 体积、展开逻辑字节、实际磁盘占用、升级/模型导入峰值空间、进程树工作集和运行库加载路径。这些资源数据只作披露。
5. 发行包绑定 SHA-256、构建配置与基线。单管线、无 OCR 是用户通过本地模型管理得到的运行状态，均从同一标准包变更后复验。

“出厂附带哪些管线”由构建清单决定；用户可在运行前后从本地介质调整已安装集合。运行策略决定其中哪些先初始化。`recognition.model_directory` 沿用数据根内的目录规则，`model_id` 沿用既有请求语义。用户把模型 ID 设为空时按当前配置约定禁用文字识别。[数据与配置](../02-数据结构.md) · [识别协议](../03-IPC协议.md)

## 已确认支持本地增减模型

- **介质来源**。发布者从许可可再分发的离线权重生成模型包，随发行 ZIP 交付或另行提供本地文件。可信模型目录内置于应用发行版本，列出模型 ID、版本、支持的引擎/格式、语言、逐文件长度、SHA-256、上游出处和许可。导入仅接受该目录认可的本地介质；新增受信版本随离线应用更新进入目录。
- **初始内容**。程序核心与可变模型数据分别列清单，出厂模型放在解压根的模型库内，安装状态保存在同一数据根。核心文件的完整性校验始终生效。对用户已提交的模型变更，以当前有效目录为准，重启无需补回主动移除的模型。
- **导入**。先列出将增加或更新的模型及磁盘占用。将临时文件写到模型库同一卷，限制声明大小，拒绝越界路径、重解析点、未知依赖和不兼容版本；完成文件校验和隔离加载探针后提交。重复导入相同内容返回当前状态。
- **提交**。内容按已校验哈希存放。模型库加写锁，比较预期修订，写出新的完整目录，在同卷原子替换当前目录指针。提交前失败或断电时旧目录继续有效；提交后按指针恢复，清理未引用的临时内容。模型清单与原发行包哈希分开留档。
- **移除**。显示依赖此模型的目标、脚本或配置中可静态识别的引用，提示动态引用在运行时解析。确认后原子提交新目录，停止接收该模型的新作业，旧作业持有原修订至终态再释放。回收仅作用于无其他管线或作业引用的文件，恢复时可重新导入同版本介质。
- **用户数据**。增减模型保留目标和脚本的原始模型 ID。模型缺失时返回相应能力错误，公开能力和语言按当前可用管线刷新。并发变更、空间不足、损坏、在用移除和同版本恢复均要保留操作结果。

## 引擎启动顺序

1. Rust 建立数据根与受管会话。Python 完成仓库、Lua VM、执行控制及适用输入守卫的必要检查后发送现有 `system_ready`，首事件序号仍为 1。
2. 纯脚本在必需能力就绪后允许执行；依赖输入租约、窗口绑定的动作继续走现有检查。启动期间 OCR 可披露为 `pending`。[协议与时限](../03-IPC协议.md)
3. 默认在首次实际请求时，以模型 ID 定位一套管线，在隔离进程按管线校验、导入和构造。只要 OCR 请求就绪即可并行初始化；纯 Lua 首句不等待 OCR 或 ORB。已初始化的同一管线可供后续作业复用。
4. 同一会话对同一管线的并发请求共享一次初始化。以作业总预算约束排队和初始化，保留独立的 5 秒推理期限；等待任务可取消。若最后一个等待者取消且管线仍在初始化，回收其隔离进程并释放资源。
5. 正常命令仍在 5 秒内受理。首个请求返回 job_id 后，作业进入有界的初始化等待。失败按模型缺失、损坏、推理超时、取消分别映射现有错误或终态。产品 10 秒体验门槛从双击起算，不能用响应受理或初始化结束替代。
6. 会话结束时中止其初始化，回收隔离子进程；按会话和作业 ID 丢弃旧结果。损坏的管线应给出可定位的错误，健康管线和纯脚本仍可运行。
7. 各管线就绪后更新能力快照。现协议已有状态枚举、`hello.model_manifests` 和单模型请求；运行中刷新能力、待加载与部分失败如何对旧调用者呈现，须在 02/03/06 及跨端测试中先冻结。避免重复发送 `system_ready`。

实现入口为 [视觉服务装配](../../backend/vision/registry.py)、[隔离进程](../../backend/vision/process_provider.py)、[模型校验](../../backend/vision/providers/ocr_models.py) 和 [Python 主入口](../../backend/main.py)。预热失败要持有模型 ID、原因和恢复方式。重新验证同一份离线模型或重启后可以再次尝试，保留第一次错误的诊断。

## 已确认的完全便携行为与兼容设计

| 情形 | 期望行为 |
|---|---|
| 当前安装版 | 既有安装流程继续使用安装收据和有效 data-root.txt。便携入口由介质清单明确标识，缺少安装绑定不能触发隐式模式切换。 |
| 全新便携包 | 完整解压到可写本地目录，双击 EXE 即启动。以 EXE 所在目录为锚点解析相对数据根 data/；账户路径、当前工作目录、盘符均不作为绑定依据。 |
| 随目录移动或复制 | 设置、脚本、目标、资产、模型、缓存、日志和备份全部留在解压目录内，Python/Paddle 派生数据也须定向至此。退出后整体移动，再启动可读原数据。复制的两份目录可分别写入各自的库。 |
| 升级便携版 | 新版本解压在另一可写目录，显式复制或导入旧便携数据及本地模型；验证 schema、模型兼容、记录数和资产哈希后启用。旧目录在验证结束前保留可用。 |
| 迁移旧安装 | 用户可选择把某个已安装版的数据根复制进便携目录。仅在用户选择迁移时读取旧位置，多个旧根展示记录数供选择。用快照和校验保留原库，成功后便携版只访问新副本。 |
| 只读目录 | 检查解压根和应用数据位置可写性。失败时提示把整个解压目录复制或迁移到可写位置，并从新位置启动；禁止静默回退 AppData、临时目录或其他用户目录。 |
| 数据根不可用 | 数据损坏、空间不足、持锁或路径越界时停止有影响的写入并给出具体恢复信息。在同一目录修复或整体迁移后重试；等待者不得并行初始化已有库。 |
| 损坏或部分解压 | 依据包内清单核对核心运行库、宿主和资源完整性；核心文件损坏时中止。按本包声明区分未附带模型与文件损坏，并报告受影响的管线。 |

首次启动以会话锁和原子替换提交解压目录内的布局版本；检查路径落在所选解压根内。运行时解析相对位置，无需用户改 PATH 或编写绝对路径文件。程序文件与可写数据分开置于同一个解压根，为只读失败、目录搬迁和升级回退记录原始用例。
旧根探测与恢复可复用 [安装器](../../tools/packaging/Install.ps1)、[旧根检查](../../tools/packaging/inspect_root.py) 和 [备份服务](../../backend/storage/backup.py)。用户指引应说明：删除整个解压目录会同时删除其中的应用数据，保留数据时先复制或导出备份。

## 验收与原始记录

在上述现有测试机上，标准完整便携包的两项指标均从**双击 EXE** 起算。预置纯 Lua 脚本执行第一条语句的 p95 ≤3 秒。预置 OCR 脚本实际拿到第一段正确、非空文字的 p95 ≤10 秒，通用与韩文管线分别判定。后者计入主窗、宿主和引擎启动、模型加载、推理及文字返回 Lua。RC16 的 7.62 秒记录使用引擎就绪终点，无法判定新门槛。

1. 在固定测试机使用同一 Windows build、磁盘、显示、电源计划和 CPU 推理配置，先固定包 SHA-256、模型目录及夹具哈希。预置三份可复核的数据根快照，分别只含相应启动脚本、固定输入资产、设置及初始模型状态；清空业务结果缓存、运行日志和框架缓存。另用空白数据根独立复验首次创建与离线能力。
2. 每轮在可写目录准备同一完整介质，为该轮复制一份从未启动的快照。结束上轮程序及所有子进程，核对进程表清空，开始时两管线均未加载。Windows 保持同次开机且保留系统文件页缓存，不清空或人工预读。记录启动时间、空闲负载和最近一次重启，不把这些样本标为重启机器后的冷盘时间。
3. 用桌面探针向资源管理器中的实际 EXE 发出双击，在发出第二次点击时记录单调时钟起点。以已选定的预置夹具，经正常启动与执行入口运行脚本，保留初始化、协议和租约检查。Lua 首句或 OCR 返回由同一时间基准打点，核验脚本标识、执行 ID 与预期文字。
4. 三组依次轮转，每组 20 个独立新进程样本。在各组内按耗时升序，nearest-rank p95 为第 19 个。失败、错误文字、提前退出和超时保留在原样本并按无穷耗时排序；任一功能失败必须复验，未关闭前不通过。每组附原始 20 行、p50、p95、最大值和失败数，重测保留旧批次。
5. 热测独立于冷启动判定。同一进程完成管线加载后，对每套管线各跑 20 次，记录从脚本发出 OCR 请求至脚本取得正确文字。使用预先冻结的不同输入，核对实际推理调用，避免复用旧识别结果。另报同一进程纯 Lua 再执行 20 次的受理至首句时间。

| 用例 | 记录与断言 |
|---|---|
| 介质与离线 | 每种已批准配置在现有 Windows x64 用普通权限、新解压根及隔离数据根执行。记录 OS build、显示配置、ZIP 与清单哈希、实际进程树、加载路径和全程网络观测。 |
| 启动时钟 | 同一单调时钟或可比对的宿主时钟记录 EXE 启动、system_ready、execute_script 受理、首句在 Lua 执行时的标记、脚本完成、首次 OCR 请求与取得正确结果。使用 session_id、execution_id、job_id 对齐，日志落盘和轮询显示延迟另报。保留从启动及从 OCR 请求两种耗时以便核对。 |
| 脚本夹具 | 使用预置且内容固定的纯 Lua 脚本，首句 log 写唯一标记并返回常量。就绪即由正常宿主发起执行，校验返回值。涉及输入时另用专窗记录首个真实动作，保留租约、焦点与停止检查。 |
| 冷热样本 | 两套 OCR 各绑定一张已知正确首段文字的图片，分开报冷启动 20 轮与热推理 20 轮。完整包的纯脚本同样保留两套模型。热测开始前核对模型进程仍存活。 |
| 性能影响 | 比较默认完整包与候选策略的首条纯脚本、首次 OCR 与热 OCR，记录初始化峰值工作集、常驻内存、子进程数。不同管线并发、取消、关闭、重启后验证资源回收。 |
| 能力一致性 | 对空选择、单管线、完整管线验模型列表、语言披露、正常识别、空结果、缺/坏权重、超时及取消。用已存在的脚本引用缺失模型，核对错误和纯脚本继续成功。 |
| 模型变更 | 逐个录入安装前后目录修订及模型哈希。覆盖离线导入、重复导入、使用中移除、引用共享文件、损坏、版本不兼容、取消、崩溃重开与从相同介质恢复；核对模型列表和真实识别结果。 |
| 数据恢复 | 分别测只读解压根、不可写子目录、改变盘符、复制并分别运行、升级与显式旧根迁移、进程持锁和中断重试。追踪应用进程树的文件写入，确认配置、模型、缓存、备份、日志均留在解压根；恢复后运行一条旧脚本。 |

包级检查参考 [验收矩阵](验收与测试.md) 的 TEST-002、TEST-014、TEST-016，并复用 [安装介质检查](../../tests/acceptance/installed_media.py) 和 [启动字节码检查](../../tests/acceptance/startup_bytecode.py)。OCR 质量使用对应数据集逐语言验；现行产品质量门槛及平台范围以[产品定义](../product/产品定义.md)为准。
每次尝试保留候选哈希、来源基线、环境、命令、预期、实际、原始记录哈希和审查者。原失败、重试和回归分开存放。跨包或旧版本的数字仅供定位，一种配置的通过情况不可移作另一种候选的验收结果。
